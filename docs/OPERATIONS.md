# 運用手順書 — SmileQ Live

会場でクイズを実施するための準備・当日運用・振り返りの手順です。

---

## 1. 開催前（前日まで）

### 1.1 コンテンツ確認

- [ ] クイズ内容と正解を**別の人**が確認した
- [ ] 数値問題の正解値・許容誤差・範囲・単位を確認した
- [ ] 2択・3択・4択・5択それぞれの投影レイアウトを確認した
- [ ] 問題画像・選択肢画像・正解解説画像が投影で読めるか確認した
- [ ] 画像のみの問題・選択肢に代替テキストを設定した
- [ ] クイズを「公開」状態にした（公開チェックがすべて通っている）

### 1.2 システム確認

- [ ] `npm run deploy:doctor` が通る
- [ ] 本番の `/api/health` が 200 を返す
- [ ] 管理画面へログインできる（司会者全員の `profiles/{uid}` が登録済み）
- [ ] **Security Rules とインデックスを反映済み**（`npm run rules:deploy -- production`）
      — 複合インデックスの構築には数分かかり、構築中はクエリが失敗します
- [ ] Cloud Run の **最小インスタンスが 1 以上**（開催日は 1 以上にする）

```bash
gcloud run services update smileq-live \
  --min-instances 1 --region asia-northeast1 --project <PROJECT>
```

- [ ] 想定人数に対して `maxInstances` と `concurrency` が十分
      （目安: 500 人 / concurrency 80 → 最大 6〜7 インスタンス。余裕を見て `maxInstances` は 10）
- [ ] ルーム作成時の**定員が想定人数以上**（既定 500 人。超えた人は入れません）
- [ ] Cloud Logging にログが出ている
- [ ] アラートの通知先を確認した

### 1.3 効果音

**差し替えはデプロイし直さずにできます。**
管理画面 → **効果音** で、9 音を 1 つずつ入れ替えられます。

- [ ] 管理画面 → 効果音 で、鳴らしたい音になっている（その場で試聴できます）
- [ ] 同梱音のまま使う場合は `npm run sounds:check` が 9 件すべて通る

| タイミング           | ファイル         |
| -------------------- | ---------------- |
| 回答受付開始         | `question-start` |
| 回答受付の間ずっと   | `tick`           |
| 回答締切             | `answer-lock`    |
| 正解発表             | `answer-reveal`  |
| ランキング           | `ranking`        |
| ランキングが出た瞬間 | `fanfare`        |
| クイズ終了           | `finish`         |
| 抽選のルーレット中   | `draw-spin`      |
| 当選が確定した瞬間   | `draw-win`       |

`tick` と `draw-spin` は**繰り返し**鳴らします。差し替えるときは
**1 秒ちょうどで、頭と末尾が無音の素材**を選んでください（継ぎ目で拍が崩れます）。

#### 管理画面から差し替える（推奨）

管理画面 → **効果音** → 差し替えたい音の「音を差し替える」。

- MP3・WAV・OGG・M4A・AAC を受け付けます（8MB まで）
- 形式は拡張子ではなく**中身**で見ます。名前だけ変えたファイルは弾かれます
- 差し替えた音は**すべての会**（クイズ・抽選会・ビンゴ・ルーレット）で鳴ります
- 反映は**次に投影画面を開いたとき**から。会の途中で差し替えたら投影画面を再読み込みします
- 「同梱の音へ戻す」でいつでも元へ戻せます

差し替えた音はリポジトリではなく**保存先（Cloud Storage）**へ入り、
自分のドメイン（`/api/sounds/...`）から配られます。
効果音ラボの規約が**素材の再配布と直リンクを禁じている**ため、この形にしています。

#### リポジトリへ同梱する（既定音を入れ替えたいとき）

`npm run sounds:install` で `public/sounds/` を差し替え、デプロイし直します。
一度作った設定を全員へ配りたいときだけ使ってください。
ふだんの差し替えは管理画面のほうが速く、失敗しても戻せます。

### 1.4 デモ（人に見せる）

- **このルームのデモ** … 投影画面の右上「デモで試す」。
  用意した抽選リストをそのまま使い、当日と同じ画面・同じ効果音で回せます。
  引くのはブラウザの中だけで、本番の記録は 1 件も動きません。
- **見本のデモ** … `/present/demo`。ルームもログインも要りません。
  抽選会・ビンゴ・ルーレットを切り替えられます。URL をそのまま人へ渡せます。

抽選会・ビンゴ・ルーレットの進め方は [docs/DRAW_MODES.md](./DRAW_MODES.md) にまとめています。

## 2. 開催前（当日・会場）

### 2.1 機材

- [ ] 電源・映像出力（HDMI 等）・音声出力・ネットワークを確認
- [ ] 投影 PC の**通知・スリープ・自動更新を抑止**
- [ ] 投影ブラウザは Chrome または Edge の現行版
- [ ] 会場 Wi-Fi とは**別の予備回線**（テザリング等）を用意

### 2.2 リハーサル

1. 管理画面でルームを作成する
2. 投影画面 `/present/[roomId]` を開く
   - **参加用の二次元コードは自動で出ます。** URL を貼り付ける必要はありません。
   - 画面はすぐ動き始めます。効果音だけは、ブラウザに止められていると鳴りません。
   - 投影用リンクの**URLはそのまま人に渡せます**。渡された人はログイン無しで
     同じ画面を開けます（何人でも）。投影画面のURL（/present/…）は本人しか開けません
3. **効果音の確認**
   - 音が鳴らない状態のときだけ、画面の下に「効果音はまだ鳴りません」の帯が出ます。
   - **画面のどこかをクリックすれば鳴るようになります**（専用のボタンを押す必要はありません）。
   - 帯の「音を出してテスト」を押すと、会場のスピーカーで確認できます。
4. 右下の操作で音量を調整し、全画面表示にする
5. **会場後方から実機で二次元コードを読み取れるか確認する**
6. iPhone と Android で 1 問ずつ通す
7. 参加時にコード入力を求められないことを確認する
8. 回答済み人数が投影へ反映されることを確認する
9. 正解発表で集計・解説・画像が表示されることを確認する

> 投影 PC のブラウザ設定で、このサイトの「音声の自動再生」を許可しておくと、
> クリックすら要らなくなります（Chrome: サイトの設定 → 音声 → 許可）。

### 2.3 別端末で投影する場合

司会画面から「投影用リンクを発行」します。

- 有効期限は既定 8 時間
- 投影端末には**進行変更の権限はありません**（表示と受信のみ）
- リンクを開くと `presenter` として登録され、`/present/[roomId]` へ遷移します
- 参加用の二次元コードは、この端末でも自動で出ます

> この機能が入る前に作られたルームだけは、サーバーが参加 URL を持っていません。
> その場合は司会画面で「参加URLを再発行」してください（以降は自動で出ます）。

### 2.4 途中から来た人を入れる

クイズ設定の「参加用の二次元コードをずっと表示する」をオンにすると、
出題中も投影画面の右下に小さな二次元コードが出続けます。
遅れて来た人が進行を止めずに参加できます（受付を締め切っている間は出ません）。

## 3. 開催中

### 3.1 標準の進行

```text
待機（QR 表示） → 問題を表示 → 回答受付を開始 → 回答を締め切る
  → 正解を発表 → （ランキングを表示） → 次の問題 → … → クイズを終了
```

### 3.2 運用のポイント

- 参加人数とオンライン人数を確認してから第 1 問へ進む
- **問題表示後、画像の読み込みを確認してから回答受付を開始する**
- 回答率を見て手動締切を調整する（時間切れでも自動的に締め切られます）
- **正解発表前に回答内訳を見せない**（司会画面でも締切後まで表示されません）
- 数値回答の代表値は締切後だけ表示する
- 通信警告が出たら、投影画面が Snapshot を再取得して復帰したか確認する

### 3.3 参加 URL を再発行したとき

- 投影画面の二次元コードが更新されたことを確認する
- 古い URL は即座に無効になる
- **既に参加済みの参加者は退出しません**（そのまま継続できます）

### 3.4 トラブル時

| 症状                         | 対応                                                                                                                                                                 |
| ---------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 投影画面が「再接続中」のまま | 画面を閉じない。ネットワーク復帰後に自動で Snapshot を取り直す。改善しなければ再読み込み                                                                             |
| 参加者が回答できない         | 現在フェーズが「回答受付中」か確認。締切済みなら次の問題へ                                                                                                           |
| 参加者の画面が固まった       | 参加者にページ再読み込みを案内（ニックネーム再入力は不要）                                                                                                           |
| 司会ボタンが 409 になる      | 別端末で操作された可能性。画面が自動更新されるので最新状態で操作し直す                                                                                               |
| 二次元コードが読めない       | 司会画面から参加 URL をコピーし、チャット等で共有（コード入力へは戻さない）                                                                                          |
| 音が鳴らない                 | 投影画面のどこかをクリックする。それでも駄目なら右下の「効果音を有効にする」→ 出力先とミュートを確認。素材が載っているかは `npm run sounds:check -- --url <公開URL>` |
| 差し替えた音が鳴らない       | 投影画面を再読み込みする（開いたときの一覧をそのまま使うため）。管理画面 → 効果音 で試聴できるかも確かめる                                                           |
| 差し替えた音だけ鳴らない     | 管理画面で試聴して確かめる。鳴らなければ形式の問題。MP3 で保存し直す                                                                                                 |
| 音を差し替えられない         | `npm run media:doctor` で保存先を確認する（画像と同じ保存先を使います）                                                                                              |
| 二次元コードが出ない         | 抽選会・ビンゴのルームでは出ません（参加者が来ないため）。クイズで出ない場合は、この機能より前に作られたルームなので「参加URLを再発行」してください                  |
| 画像をアップロードできない   | 出たメッセージをそのまま読む（原因が添えてあります）。切り分けは `npm run media:doctor -- --file <失敗した画像>`                                                     |

> **回答を失う「ルーム初期化」機能はありません。** 誤操作の巻き戻しより、状態遷移の単純さと監査性を優先しています。

## 4. 開催後

- [ ] ルームを「終了」状態にする
- [ ] 必要なログと結果を保存する
- [ ] 保存期間に従って参加者情報（ニックネーム）を削除・匿名化する
- [ ] エラーログ・通信状況・回答遅延を振り返る
- [ ] 次回の改善事項を Issue へ登録する
- [ ] **Cloud Run の最小インスタンスを 0 へ戻す**（費用削減）

```bash
gcloud run services update smileq-live \
  --min-instances 0 --region asia-northeast1 --project <PROJECT>
```

### 参加者情報の削除・匿名化

ニックネームは `rooms/{roomId}/members/{memberId}` の `nickname` / `nicknameLower` に入っています。
回答データと得点（`totalPoints` / `correctCount`）は残したまま、表示名だけを匿名化します。

**Firebase コンソールから手作業で消さないでください。** 件数が多く、消し漏れが起きます。
Admin SDK を使うスクリプト（`scripts/host-admin.mjs` と同じ ADC の作法）で一括処理してください。

```text
rooms/{roomId}/members を role=='participant' で読み、
  nickname       → '参加者' + memberId の先頭 8 文字
  nicknameLower  → 同じ値の小文字
へ一括更新する（バッチ書き込みは 500 件ずつ）
```

匿名認証ユーザー自体の整理は Firebase コンソールの
**Authentication → ユーザー**、または Admin SDK の `deleteUsers()` で行います。

## 5. 監視

### 5.1 最低限見る指標

| 指標                        | 目安                          | 確認方法                            |
| --------------------------- | ----------------------------- | ----------------------------------- |
| Cloud Run 5xx 率            | 1% 未満                       | Cloud Monitoring                    |
| p95 レスポンス時間          | 回答 API 1 秒以内             | Cloud Monitoring                    |
| インスタンス数              | `maxInstances` に張り付かない | Cloud Monitoring                    |
| コンテナ起動失敗            | 0                             | Cloud Logging                       |
| `/api/health`               | 常に 200                      | 稼働監視                            |
| 回答 API の 409 / 422 / 429 | 急増しない                    | ログのフィルタ                      |
| 画像変換失敗                | 0                             | `errorCode=MEDIA_PROCESSING_FAILED` |

Firestore 固有の指標:

| 指標                           | 目安                                             | 確認方法                                                         |
| ------------------------------ | ------------------------------------------------ | ---------------------------------------------------------------- |
| ドキュメント書き込み回数       | 想定（参加人数 × 問題数 + 状態遷移）から外れない | Cloud Monitoring `firestore.googleapis.com/document/write_count` |
| ドキュメント読み取り回数       | 急増しない（費用に直結）                         | `firestore.googleapis.com/document/read_count`                   |
| トランザクションの競合         | 開催中に増え続けない                             | ログの `STATE_VERSION_CONFLICT`                                  |
| **`PERMISSION_DENIED`**        | **0**（出たら Rules と実装の不一致）             | `errorCode` のフィルタ                                           |
| インデックス未整備             | 0                                                | ログの `FAILED_PRECONDITION` / `requires an index`               |
| 進捗ドキュメントの書き込み競合 | 発生しない                                       | `severity=WARNING` のログ                                        |

> **`PERMISSION_DENIED` と `requires an index` は開催中に出てはいけない種類のエラー**です。
> 前者は Rules を反映し忘れたか実装がずれた合図、後者はインデックス未反映の合図で、
> どちらも「前日までに `npm run rules:deploy` を実行したか」で防げます。

### 5.2 ログの見方

構造化 JSON ログを stdout / stderr へ出力し、Cloud Logging が収集します。

```bash
# リアルタイムに追う
gcloud run services logs tail smileq-live --region asia-northeast1 --project <PROJECT>

# エラーだけ
gcloud logging read \
  'resource.type=cloud_run_revision AND resource.labels.service_name=smileq-live AND severity>=ERROR' \
  --project <PROJECT> --limit 50 --format json
```

ログに含まれるフィールド:

```text
severity / timestamp / service / environment / requestId / route / method
userId / roomId / questionId / action / stateVersion / result / errorCode / durationMs
```

**記録されないもの**（意図的に除外しています）:
Firebase の ID トークン・セッションクッキー、参加トークン平文、投影トークン平文、
正解発表前の正解データ、数値回答の生入力。
参加 URL は `/j/[redacted]` にマスクされます。

> Firebase 版には**サーバー用の秘密情報がそもそも存在しません**（Cloud Run の ADC で認証）。
> 「鍵がログへ出た」という事故の余地自体を無くしています。

### 5.3 推奨アラート

| 条件                                   | 通知                     |
| -------------------------------------- | ------------------------ |
| 5xx 率が 5 分間 5% 超                  | 即時                     |
| `/api/health` が 2 回連続失敗          | 即時                     |
| コンテナ起動失敗                       | 即時                     |
| `PERMISSION_DENIED` が 1 件でも発生    | 即時（Rules の反映漏れ） |
| インスタンス数が `maxInstances` に到達 | 開催中のみ               |
| Firestore の読み取り回数が想定の 3 倍  | 日次（費用の異常検知）   |

開催前後の時間帯だけでも通知先を確認しておいてください。

## 6. 費用の調整

| 項目                     | イベント期間                       | 平常時                   |
| ------------------------ | ---------------------------------- | ------------------------ |
| Cloud Run `minInstances` | 1                                  | 0                        |
| Cloud Run `maxInstances` | 10                                 | 5                        |
| ロードバランサ           | 使う場合は常時課金                 | 停止するなら削除が必要   |
| Firestore                | 読み書き回数とストレージの従量課金 | 使わなければほぼ 0       |
| Cloud Storage            | 画像のストレージと転送             | 古いイベントの画像を整理 |

Firestore は**読み取り回数**が費用の主因です。参加者画面のポーリングを増やしたり、
不要なドキュメントを購読したりすると、人数に比例して跳ね上がります。
購読対象を `rooms/{id}/public/state` に限る設計は、秘匿だけでなく費用面の理由でもあります。

`minInstances=0` にすると、最初のアクセスでコールドスタートが発生します（数秒）。
イベント当日は必ず 1 以上にしてください。

## 7. 規模の目安

| 項目             |                     目標 |
| ---------------- | -----------------------: |
| 1 ルームの参加者 | 500 人（実測で確認済み） |
| 最大問題数       |                   100 問 |
| 標準制限時間     |                    20 秒 |
| 回答 API 応答    |          通常時 1 秒以内 |
| 状態変更の反映   |          通常時 1 秒以内 |
| 回答進捗の反映   |          通常時 2 秒以内 |
| 投影解像度       |         1920×1080 (16:9) |

### 7.1 自分で確かめる

```bash
npm run load:test                          # 既定の 500 人
npm run load:test -- --participants 1000   # 人数を変えて試す
```

Firestore エミュレータ上で、実際のトランザクションへ人数ぶんの要求を同時にぶつけます。
確かめているのは会場で同時に起きる 3 つの場面です。

1. 開場直後に全員が二次元コードを読む（参加登録が一斉に走る）
2. 出題ごとに全員が同時に回答する（回答登録が一斉に走る）
3. 正解発表で全員の画面が更新される（ランキング取得が一斉に走る）

**1 件でも落ちたら失敗**として扱います。会場では「入れなかった人」「回答できなかった人」が
出た時点で事故だからです。実行には Java が要ります（無ければスキップして成功扱い）。

### 7.2 人数が増えると何が起きるか

Firestore は **1 つのドキュメントへの書き込みが毎秒 1 回程度**を想定しています。
人数が増えて壊れるのは、たいてい「全員が同じ 1 つのドキュメントを書きに行く」場所です。
そのため次の設計にしてあります。

| 場面       | やっていること                                                                                                                                   |
| ---------- | ------------------------------------------------------------------------------------------------------------------------------------------------ |
| 参加登録   | 参加者行の作成だけを行い、人数はドキュメント単位の加算（`FieldValue.increment`）で足す。同じドキュメントを読んで書き戻すトランザクションにしない |
| 回答登録   | 書き込み先は本人の回答行と本人の得点行だけ。共有ドキュメントへは書かない                                                                         |
| 回答進捗   | `public/state` への書き込みを 400ms に 1 回まで間引く（全員が購読しているため、1 回書くと人数ぶんの読み取りが発生する）                          |
| ランキング | 得点が動かないフェーズでは、インスタンス内で一度だけ作って使い回す                                                                               |
| 在席時刻   | 30 秒以内に更新済みなら書き直さない                                                                                                              |

500 人を大きく超える場合は `npm run load:test -- --participants <人数>` で先に確かめ、
`concurrency` / `maxInstances` を調整してください。

### 7.3 定員（ROOM_FULL）

ルーム作成時に決める定員を超えた人は参加できません（既定 500 人、上限 1000 人）。
同時に来た場合は数人ぶん超えて登録されることがあります。
「入れない人を出さない」ほうを優先しているためで、運用上の目安として扱ってください。
