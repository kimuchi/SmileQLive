# 運用手順書 — SmileQ Live

会場でクイズを実施するための準備・当日運用・振り返りの手順です。

---

## 1. 開催前（前日まで）

### 1.1 コンテンツ確認

- [ ] クイズ内容と正解を**別の人**が確認した
- [ ] 数値問題の正解値・許容誤差・範囲・単位を確認した
- [ ] 2択・3択・4択・5択それぞれの投影レイアウトを確認した
- [ ] 問題画像・選択肢画像・正解解説画像が投影で読めるか確認した
- [ ] 画像のみの問題・選択肢に代替テキストを設定した
- [ ] クイズを「公開」状態にした（公開チェックがすべて通っている）

### 1.2 システム確認

- [ ] `npm run deploy:doctor` が通る
- [ ] 本番の `/api/health` が 200 を返す
- [ ] 管理画面へログインできる
- [ ] Cloud Run の **最小インスタンスが 1 以上**（開催日は 1 以上にする）

```bash
gcloud run services update smileq-live \
  --min-instances 1 --region asia-northeast1 --project <PROJECT>
```

- [ ] 想定人数に対して `maxInstances` と `concurrency` が十分
  （目安: 200 人 / concurrency 80 → 最大 3〜4 インスタンス。余裕を見て `maxInstances` は 10）
- [ ] Cloud Logging にログが出ている
- [ ] アラートの通知先を確認した

### 1.3 効果音

- [ ] `public/sounds/` に 6 種類の効果音が配置されている
- [ ] `public/sounds/LICENSE.md` に出典を記録した

| タイミング | ファイル |
|---|---|
| 回答受付開始 | `question-start` |
| 残り 5〜1 秒 | `tick` |
| 回答締切 | `answer-lock` |
| 正解発表 | `answer-reveal` |
| ランキング | `ranking` |
| クイズ終了 | `finish` |

## 2. 開催前（当日・会場）

### 2.1 機材

- [ ] 電源・映像出力（HDMI 等）・音声出力・ネットワークを確認
- [ ] 投影 PC の**通知・スリープ・自動更新を抑止**
- [ ] 投影ブラウザは Chrome または Edge の現行版
- [ ] 会場 Wi-Fi とは**別の予備回線**（テザリング等）を用意

### 2.2 リハーサル

1. 管理画面でルームを作成する
2. 投影画面 `/present/[roomId]` を開く
3. **「投影を開始して音声を有効化」をクリック**（クリック前は音が鳴りません）
4. 音声テストで会場の音量を確認する
5. 全画面表示にする
6. **会場後方から実機で二次元コードを読み取れるか確認する**
7. iPhone と Android で 1 問ずつ通す
8. 参加時にコード入力を求められないことを確認する
9. 回答済み人数が投影へ反映されることを確認する
10. 正解発表で集計・解説・画像が表示されることを確認する

### 2.3 別端末で投影する場合

司会画面から「投影用リンクを発行」します。

- 有効期限は既定 8 時間
- 投影端末には**進行変更の権限はありません**（表示と受信のみ）
- リンクを開くと `presenter` として登録され、`/present/[roomId]` へ遷移します

## 3. 開催中

### 3.1 標準の進行

```text
待機（QR 表示） → 問題を表示 → 回答受付を開始 → 回答を締め切る
  → 正解を発表 → （ランキングを表示） → 次の問題 → … → クイズを終了
```

### 3.2 運用のポイント

- 参加人数とオンライン人数を確認してから第 1 問へ進む
- **問題表示後、画像の読み込みを確認してから回答受付を開始する**
- 回答率を見て手動締切を調整する（時間切れでも自動的に締め切られます）
- **正解発表前に回答内訳を見せない**（司会画面でも締切後まで表示されません）
- 数値回答の代表値は締切後だけ表示する
- 通信警告が出たら、投影画面が Snapshot を再取得して復帰したか確認する

### 3.3 参加 URL を再発行したとき

- 投影画面の二次元コードが更新されたことを確認する
- 古い URL は即座に無効になる
- **既に参加済みの参加者は退出しません**（そのまま継続できます）

### 3.4 トラブル時

| 症状 | 対応 |
|---|---|
| 投影画面が「再接続中」のまま | 画面を閉じない。ネットワーク復帰後に自動で Snapshot を取り直す。改善しなければ再読み込み（音声有効化からやり直し） |
| 参加者が回答できない | 現在フェーズが「回答受付中」か確認。締切済みなら次の問題へ |
| 参加者の画面が固まった | 参加者にページ再読み込みを案内（ニックネーム再入力は不要） |
| 司会ボタンが 409 になる | 別端末で操作された可能性。画面が自動更新されるので最新状態で操作し直す |
| 二次元コードが読めない | 司会画面から参加 URL をコピーし、チャット等で共有（コード入力へは戻さない） |
| 音が鳴らない | 投影画面を再読み込みし、オーバーレイのボタンから音声を有効化し直す |

> **回答を失う「ルーム初期化」機能はありません。** 誤操作の巻き戻しより、状態遷移の単純さと監査性を優先しています。

## 4. 開催後

- [ ] ルームを「終了」状態にする
- [ ] 必要なログと結果を保存する
- [ ] 保存期間に従って参加者情報（ニックネーム）を削除・匿名化する
- [ ] エラーログ・通信状況・回答遅延を振り返る
- [ ] 次回の改善事項を Issue へ登録する
- [ ] **Cloud Run の最小インスタンスを 0 へ戻す**（費用削減）

```bash
gcloud run services update smileq-live \
  --min-instances 0 --region asia-northeast1 --project <PROJECT>
```

### 参加者情報の削除例

```sql
-- ニックネームを匿名化（回答データと得点は残す）
update public.room_members
set nickname = '参加者' || substr(id::text, 1, 8)
where room_id = '<ROOM_ID>' and role = 'participant';
```

## 5. 監視

### 5.1 最低限見る指標

| 指標 | 目安 | 確認方法 |
|---|---|---|
| Cloud Run 5xx 率 | 1% 未満 | Cloud Monitoring |
| p95 レスポンス時間 | 回答 API 1 秒以内 | Cloud Monitoring |
| インスタンス数 | `maxInstances` に張り付かない | Cloud Monitoring |
| コンテナ起動失敗 | 0 | Cloud Logging |
| `/api/health` | 常に 200 | 稼働監視 |
| 回答 API の 409 / 422 / 429 | 急増しない | ログのフィルタ |
| Realtime 送信失敗 | 0 に近い | `severity=WARNING` のログ |
| 画像変換失敗 | 0 | `errorCode=MEDIA_PROCESSING_FAILED` |

### 5.2 ログの見方

構造化 JSON ログを stdout / stderr へ出力し、Cloud Logging が収集します。

```bash
# リアルタイムに追う
gcloud run services logs tail smileq-live --region asia-northeast1 --project <PROJECT>

# エラーだけ
gcloud logging read \
  'resource.type=cloud_run_revision AND resource.labels.service_name=smileq-live AND severity>=ERROR' \
  --project <PROJECT> --limit 50 --format json
```

ログに含まれるフィールド:

```text
severity / timestamp / service / environment / requestId / route / method
userId / roomId / questionId / action / stateVersion / result / errorCode / durationMs
```

**記録されないもの**（意図的に除外しています）:
Supabase Secret Key、Auth アクセストークン、参加トークン平文、投影トークン平文、
正解発表前の正解データ、数値回答の生入力。
参加 URL は `/j/[redacted]` にマスクされます。

### 5.3 推奨アラート

| 条件 | 通知 |
|---|---|
| 5xx 率が 5 分間 5% 超 | 即時 |
| `/api/health` が 2 回連続失敗 | 即時 |
| コンテナ起動失敗 | 即時 |
| インスタンス数が `maxInstances` に到達 | 開催中のみ |

開催前後の時間帯だけでも通知先を確認しておいてください。

## 6. 費用の調整

| 項目 | イベント期間 | 平常時 |
|---|---|---|
| Cloud Run `minInstances` | 1 | 0 |
| Cloud Run `maxInstances` | 10 | 5 |
| ロードバランサ | 使う場合は常時課金 | 停止するなら削除が必要 |
| Supabase | プランに依存 | — |

`minInstances=0` にすると、最初のアクセスでコールドスタートが発生します（数秒）。
イベント当日は必ず 1 以上にしてください。

---

## 7. 規模の目安

| 項目 | 初期目標 |
|---|---:|
| 1 ルームの参加者 | 200 人 |
| 最大問題数 | 100 問 |
| 標準制限時間 | 20 秒 |
| 回答 API 応答 | 通常時 1 秒以内 |
| 状態変更の反映 | 通常時 1 秒以内 |
| 回答進捗の反映 | 通常時 2 秒以内 |
| 投影解像度 | 1920×1080 (16:9) |

200 人を超える場合は、負荷試験で回答進捗イベントの集約間隔（250〜500ms）と
`concurrency` / `maxInstances` を調整してください。
